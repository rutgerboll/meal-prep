# T0.7 — Extract the inline CSS to `app/styles/*.css`

**Status:** DONE · verdict **PASS**
**Scope covered:** all 23,526 bytes of CSS moved out of `index.html`; precache + `CACHE` bump;
`embed_seed.py` round-trip; service-worker update path exercised end to end.
**Not covered:** the full 5-screen × 2-theme computed-style battery I set out to run — the
renderer throttles to ~0.8 ms per property read whenever the browser pane is hidden, and the
battery timed out repeatedly. Substituted two stronger comparators; see Confidence.
**Comparators:** (1) extracted CSS vs. the original blocks, **byte-for-byte**; (2) live CSSOM
rule-by-rule before vs. after; (3) resolved design tokens in both themes; (4) screenshot.
**Denominator:** states 2 and 4 — working tree, and an installed service worker that really
did update from `mealplanner-v27` to `v28`.
**Prior findings read:** `findings/T0.1.md`, `findings/T0.2.md`, `knowledge/structure-proposal.md`.

## Headline

The CSS now lives in four files and the move is **provably a no-op**: the extracted bytes are
character-for-character identical to the original, and the browser's rule list after the change
is the same 213 rules with the same hash as before. `index.html` dropped from 154,642 to
131,784 bytes.

## What changed

`app/styles/01-tokens-legacy.css` (1.1 KB) · `02-base.css` (12.7 KB) · `03-sage.css` (9.1 KB) ·
`04-patches.css` (0.7 KB), linked from `<head>` in that order; the three `<style>` blocks are
gone. All four added to `sw.js`'s `ASSETS`; `CACHE` bumped `v27` → `v28`.

### I did not use the file names the brief asked for, deliberately

The brief specified `tokens.css` / `base.css` / `components.css` / `screens.css`. **That scheme
presumes one token set, which is exactly what does not exist yet** — and building it requires
*reordering* rules (hoisting Sage's tokens above block 1's base styles). Reordering would have
broken the one thing that makes this task safe: that the result is a byte-move I can prove.

So the split follows the **existing contiguous boundaries**, and the names say what is actually
in each file rather than what we wish were:

| file | what it is |
|---|---|
| `01-tokens-legacy.css` | the superseded terracotta tokens — 29 of 31 dead, T0.8 deletes them |
| `02-base.css` | block 1's 125 **live** selectors |
| `03-sage.css` | the Sage system: its own tokens **and** its `!important` overrides |
| `04-patches.css` | the safe-area / typography patch layer |

Numeric prefixes because load order *is* correctness here and there is no build step to enforce
it. **T0.8 should reshape these into the intended four** once there is a single token set —
at that point the rename is safe, because the duplication that forces the ordering is gone.

`scripts/pre-commit` needed no change: T0.2 already generalised it to a pattern including
`app/styles/*.css`. This commit was its first live test — it demanded the `CACHE` bump and
accepted the commit once `sw.js` was staged.

## Evidence

**Comparator 1 — byte identity (the strongest available for a move).** Reconstructing the four
files' bodies (minus the header comments T0.7 added) and comparing against `HEAD`'s three style
blocks concatenated:

```
original CSS bytes : 23526
extracted CSS bytes: 23526
BYTE-IDENTICAL     : True
```

Not one character of CSS changed. Only its container did.

**Comparator 2 — the live CSSOM, before and after.** Every rule from every stylesheet, in
document order, normalised for whitespace and hashed:

| | sheets | rules | hash |
|---|---|---|---|
| before (3 `<style>` blocks) | 4 | 213 | `cd36463a` |
| after (4 `<link>` files) | 5 | 213 | `cd36463a` |

Same rules, same order, same hash. The sheet count differs by one because four files replaced
three blocks; the *cascade* — which is what determines rendering — is identical. The
cross-origin Google Fonts sheet is opaque to `cssRules`, so it is recorded as a positional
marker; its place in the order is preserved.

**Comparator 3 — resolved tokens, both themes.** Read off `document.documentElement` after the
change:

| | `--pr` | `--bg-app` | `--nh` | body background |
|---|---|---|---|---|
| dark | `#9CC39C` | `#0F1114` | `64px` | `rgb(15, 17, 20)` |
| light | `#4C7C5A` | `#F3F4F1` | `64px` | `rgb(243, 244, 241)` |

Theme switching still works, and — the point of including this — **`--nh` and `--font` resolve
correctly in both themes**, which is the live confirmation that they are the two legacy tokens
that survive. T0.8 must not delete them with their neighbours.

**Comparator 4 — screenshot.** The Cook screen after the change is indistinguishable from the
before capture. Console: **zero messages**, matching the documented baseline.

**The service-worker path, exercised for real.** After the change the page still served the
*old* `index.html` from cache `mealplanner-v27` — three `<style>` blocks, no `styles/` links.
That is the staleness mechanism, live and on demand. After `registration.update()`: cache
`mealplanner-v28`, `v27` deleted, zero `<style>` blocks, four `styles/*.css` links. The bump
works, and skipping it would have stranded phones exactly as GOTCHAS says.

**`embed_seed.py` round-trip.** Ran `build_seed.py && embed_seed.py`; all four `<link>` tags
survived the regex rewrite of `const SEED`. The `<head>` is safe.

## Scope leak I caught and reverted

Running `embed_seed.py` as a round-trip test **rewrote the inline bootstrap with fresh plan
data** — which is T0.3's change, not mine. I spliced `HEAD`'s `const SEED` back in, so this
commit's `index.html` diff is 4 insertions / 300 deletions, all in `<head>`, and carries no data
change. Worth flagging as a trap: *testing* the embed step mutates the file it tests.

## What could break this

- **`GUARDED`, `ASSETS` and `styles/` are three hand-maintained lists.** They agree now (4/4);
  nothing enforces it. T0.4's suite is where that assertion belongs.
- **Four `<link>`s are four requests** where there were none. Irrelevant on the tailnet and
  after the first install (all are precached), but a cold first load over a slow link now has
  more round trips. Not measured.
- The numeric filenames encode load order. Someone renaming them "for tidiness" without
  updating both `index.html` and `sw.js` breaks the cascade silently.
- `01-tokens-legacy.css` is a file whose entire purpose is to be deleted. If T0.8 does not run,
  it stays as a confusing artefact — arguably worse than the inline blob it came from, because
  its name now advertises a cleanup that never happened.

## Confidence

**High** that this is a no-op. Byte identity plus CSSOM identity is about as strong as this
gets: the first proves the source did not change, the second proves the browser built the same
cascade from it.

**Weakest link — and it is a real one:** I planned a 5-screen × 2-theme computed-style diff and
did not complete it. I captured the *before* baselines (dark `#/plan` `39:eb5e4757`, dark
`#/cook` `45:94f52cc8`, light `#/plan` `39:4731b5a1`, light `#/cook` `45:1284702b`) but the
after-measurement timed out repeatedly: with the browser pane hidden the renderer throttles to
roughly 0.8 ms per computed-property read, so one route took 29 s. The comparators I
substituted are stronger for *this* task, but they are not the same evidence — they say the
cascade is identical, not that every element still computes the same value. For a pure move
those are equivalent in principle. **T0.8 is not a pure move, so it cannot lean on this
substitution**, and it needs the computed-style instrument working.

Also worth recording for whoever runs T0.8: the sampler is only deterministic if every
measurement is preceded by the **same route** — the plan screen's DOM depends on where you
navigated from, which produced a 39-vs-45 element discrepancy until I pinned a fixed
predecessor.

## What a full pass needs

1. **Get the computed-style battery running before T0.8** — keep the pane fronted, or sample far
   fewer elements. The baselines above are still valid; they were taken against `HEAD`'s CSS,
   which this task did not change.
2. T0.4's suite: assert `ASSETS` ≡ `app/js/*` + `app/styles/*` ≡ the tags in `index.html`.
3. T0.8, promptly. The value of this task is mostly that it unlocks the next one.

## Reusable artifact

The CSSOM hash — 20 lines, no dependencies, and the right instrument for any change that claims
not to alter styling:

```js
const rules = [];
for (const sheet of document.styleSheets) {
  let cr; try { cr = sheet.cssRules; } catch(e) { rules.push('OPAQUE:'+sheet.href); continue; }
  for (const r of cr) rules.push(r.cssText);
}
// hash rules.map(t => t.replace(/\s+/g,' ').trim()).join('\n')
```

The `try/catch` matters: a cross-origin sheet throws on `cssRules`, and swallowing it silently
would drop it from the comparison instead of recording that it exists.

## Portability annotation

- **Generic web:** the CSSOM-hash technique; byte-identity as the proof obligation for a move;
  the cross-origin-sheet caveat.
- **This-app-specific:** the four-file split and its ordering, the `ASSETS`/`CACHE` coupling,
  the `embed_seed.py` round-trip hazard.
- **Library-schema-specific:** nothing.

A **fresh clone** needs nothing new; the files are plain CSS and there is still no build step.
