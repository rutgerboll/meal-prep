## Evidence

**Comparator pair A — code path read + observed behavior (the broken server).**
`meal-server.py` serves `directory=SCRIPT_DIR` and shells out to `build_seed.py`. Observed on
the live launchd process (pid 89492, up since 25 Jul): `/index.html` → 404, `/sw.js` → 404,
`/sync.json` → 500 `build_seed.py returned non-zero exit status 2`. Its `cwd` inode (55260529)
matches the real `app/` dir, and my shell reads those files fine — so the files existed and
that process could not read them. The same script from a shell on port 8766: 200 / 200 / 200
(1,087,727 B). Last successful sync before the outage: 2026-08-01 08:52 (mtime of the two
server-written files). `tailscale serve` proxied the phone's HTTPS URL to 127.0.0.1:8765
throughout, so the phone was hitting a 404 for three days.

*Third measurement, unplanned, which refutes my first explanation.* Cleaning up, I ran
`pkill -f "meal-server.py"` meaning to stop only my 8766 instance; it matched the launchd
process too. launchd restarted it at 14:08:33 and the fresh process is fully healthy:
200 / 155,157 B on `/index.html`, 200 on `/sw.js`, `/js/pwa.js`, `/manifest.webmanifest`,
`/icon-192.png`, 1,087,727 B on `/sync.json`, and 200 through Tailscale on the phone's own
URL. Same LaunchAgent, same plist, same interpreter. **Full Disk Access is granted and always
was**, so the cause I took from SYNC-SETUP.md — which predicts a silent crash-loop, and it did
not crash — cannot be right. What made a long-running process lose read access under
`~/Documents` while a fresh one has none of that trouble is **unknown**; untested candidates
are a TCC grant re-evaluated against an already-running process, an OS update (Darwin 25.3.0)
invalidating a running process's authorization, or a firmlink change under the path. The
restart destroyed the only specimen — which is itself the operational lesson, now in §3.

true`, 1890 B. Both halves of GOTCHAS' claim are now measured, not assumed.

**Comparator pair C — observed app behavior + the real markdown library.** The app rendered

## What could break this

- **The root cause of the 404s is unknown, and one plausible story has already been wrong
  once.** Do not let the next session re-derive the Full Disk Access explanation from
  SYNC-SETUP.md; it is refuted. Anything written about *why* is a hypothesis until someone
  captures evidence from a stuck process before restarting it.
- **The outage may recur, and would again be invisible.** Nothing monitors this. The phone
  simply fails to sync, and an installed app keeps working offline, so there is no signal.
- **The skills' cache path is session-scoped.** It resolved today; a future session may find a
  different UUID or an evicted cache. That is why §2 ships a `find`, not a path.
- **Nothing here was verified on a phone.** Every installed-state claim is Chromium-in-the-
  browser-pane with a real service worker. iOS Safari's SW eviction behaves differently.
- **The 74× figure is one machine, one library size,** and `sips` throughput is the whole
  cold cost — it will drift as photos are added.
- **§1's four-state model is a description of today's wiring.** Give the app an HTTP cache
  header or a versioned asset path and the model needs a revision, not a patch.

## What a full pass needs

1. **Find out why the server went deaf**, since a restart fixed it but nothing explains it and
   nothing would catch a recurrence. Minimum: a check that `curl`s a real path (not `lsof`)
   and says something when it fails. Next time it happens, capture `lsof`/`sample`/TCC state
   *before* restarting.
2. **Harden `deploy.sh`**: its success check is `lsof … LISTEN`, which the broken server
   satisfies. It should `curl` a real path. Likewise the dirty-checkout guard should ignore
   `app/seed.json`, which the server owns — otherwise deploy is unusable by construction.
3. **Extend `scripts/pre-commit` to `app/js/*.js`.** The gap is now measured; the fix is one
   `grep` pattern. It is the highest-leverage line of code in this repo.
4. Re-run `embed_seed.py` and commit, to close the 20-entry bootstrap drift.
5. Verify one claim on an actual phone, once, to calibrate how far browser-pane evidence
   carries.

Items 2 and 3 are real defects found in passing, out of T0.1's "do not change `app/`" scope —
they are follow-up tasks, not silent fixes.

## Portability annotation

- **Generic web:** the cache-first service-worker staleness trap and the `curl`-vs-`fetch()`
  technique for measuring it. Any offline-first PWA has this shape.
- **This-app-specific:** the four-state denominator model, the certified serve incantation,
  the launchd/FDA failure, `deploy.sh`'s guards, `app/seed.json` being server-owned.
- **Library-schema-specific:** every count in the baseline, the 20-entry drift, the 74×
  timing, and `schemaVersion: 3`.

A **fresh clone** needs: `cp scripts/pre-commit .git/hooks/pre-commit && chmod +x`;
`git config merge.ours.driver true` (per `.gitattributes`); and a cold seed build (7.4 s).
A **different phone** re-derives 4a on first sync but starts 4b at whatever `CACHE` it first
installs. An **empty library** makes `build_seed.py` fail at `RECIPES_DIR` exactly as the
worktree trap does — the pipeline has no empty-library path.
