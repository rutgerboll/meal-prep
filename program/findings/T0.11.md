# T0.11 — The directory move: `client/` `pipeline/` `server/` `docs/`

**Status:** DONE · verdict **NO-GO (defer, with a trigger)**
**Scope covered:** the decision, and a corrected cost model. **Not covered:** the move itself —
deliberately not performed.
**Comparators:** the proposal's predicted cost vs. the measured path sites · the move's
preconditions vs. the system's actual state · what the earlier tasks in this wave already
delivered vs. what the move would add.
**Denominator:** state 1/2 — repo inspection. Nothing changed.
**Prior findings read:** T0.2, T0.7, T0.8, T0.9, T0.10, T0.12, `knowledge/structure-proposal.md`.

## Headline

**Do not do the move now.** Not because it is expensive — it is *cheaper* than
`knowledge/structure-proposal.md` claimed, and I should correct that — but because its safety
precondition is unmet: the launchd job cannot start the server at all, and the move edits that
job's plist. Trigger for revisiting is stated below.

## The cost is lower than the proposal said. Two of its warnings were wrong.

I wrote the proposal's risk list from reading; measuring it changes the picture.

**Wrong #1 — "the service worker's scope changes; a scope change can orphan an installed
phone's registration."** It does not. `meal-server.py` serves with `directory=SCRIPT_DIR`, so
the web root *is* whatever directory the app files sit in. Moving `app/` → `client/` and
pointing the server at `client/` leaves every URL identical: `/index.html`, `/sw.js`,
`/js/…`, `/styles/…`. **Installed phones would see nothing at all.** That was the single
biggest risk I claimed, and it is not real.

**Wrong #2 — the `../..` depth hazard.** `meal-server.py` resolves the feedback inbox as
`SCRIPT_DIR/../..`, and `build_seed.py` defaults `BASE_DIR` the same way. `app/` and `server/`
are both one level under the repo root, so the depth is unchanged and both still resolve. I
checked rather than assumed.

**Right, and the only genuinely fiddly part:** `~/Library/LaunchAgents/com.mealplanner.server.plist`
carries an absolute path to `…/app-build/app/meal-server.py`. It lives outside the repo, so it
is not covered by any test, any hook, or `git revert` — and changing it needs a
`launchctl bootout` / `bootstrap` cycle.

Everything else is `SCRIPT_DIR`-relative and moves for free. The real path-edit list is small:
`meal-server.py`'s served directory, `deploy.sh`'s `SCRIPT_DIR/..`, `scripts/pre-commit`'s
`^app/` patterns, `CLAUDE.md`, and CONTRACT §2/§3/§8.

## Why "not now" anyway

**1. The rollback path is half-broken.** T0.11's own brief says `deploy.sh` must work first,
because it is the way back. It does — but only via its **manual fallback**: the launchd job
fails with `Operation not permitted` (T0.10, LOG #11), so production is a `nohup`'d process.
Editing the plist of a job that already cannot start, on the machine that serves the user's
phone, with no supervised path to fall back to, is the wrong order of operations. **Fix the
Full Disk Access grant, confirm `deploy.sh` reports "via launchd", then move.**

**2. The debt that was actually costing something is already gone.** The proposal's own closing
line was "the layout is a symptom, and the debt is in the CSS." That has held up:

| what hurt | fixed by |
|---|---|
| two conflicting token sets, 29 dead tokens, 20 `!important` | T0.7 + T0.8 |
| two design docs both claiming authority | T0.9 |
| permanently dirty checkout, deploy that could never run | T0.10 |
| heading font dying offline, third-party request every load | T0.12 |
| `app/js/*.js` shipping silently stale | T0.2 |

What the move adds on top is **legibility** — that `app/` holds six files the phone never runs
(`build_seed.py`, `embed_seed.py`, `apply-feedback.py`, `meal-server.py`, `deploy.sh`,
`TECH-SCOPE.md`) among the eleven it does. Real, but it is a cost paid by future sessions
reading the tree, not by the user cooking dinner. `knowledge/prioritization.md` weights
pipeline-integrity heaviest; this scores zero on it.

**3. It would churn a contract that was just frozen.** CONTRACT §2 names `app/`, `scripts/` and
`spec/` as the population; §3 and §8 carry `cd app && …` incantations. The move falsifies all
three and forces a fourth version bump in a day. Fine when the move earns it; not for tidiness.

## What I did instead: nothing, on purpose

No files moved, no paths edited. The brief authorises this outcome explicitly, and manufacturing
a partial move — say, consolidating `spec/` and `logs/` into `docs/` — would spend the same
contract-churn and reference-fixing cost for the least valuable third of the benefit. `docs/`
does now exist with one tenant (`docs/archive/`, from T0.9); that is a loose end I am naming
rather than tidying.

## The trigger for revisiting

Do the move when **both** hold:

1. Full Disk Access is granted and `./deploy.sh` prints "via launchd", not "manual background
   process" — so there is a supervised, rehearsed way back.
2. Someone is already editing the plist or `deploy.sh` for another reason, so the one genuinely
   fiddly step is not a cost this change pays alone.

Sequence when it happens: worktree → move with `git mv` → update the five path sites → run the
full chain (`build_seed.py` → `embed_seed.py` → serve → load → sync → feedback POST) → edit the
plist → `bootout`/`bootstrap` → `curl` both the local port and the Tailscale URL.

## What could break this decision

- **If the FDA grant never happens**, condition 1 never fires and this defers forever. That
  would be the wrong outcome: at that point the plist is dead weight anyway and the move should
  proceed on `deploy.sh`'s fallback alone.
- **T0.13** (the CSS rename deferred from T0.8) overlaps this decision. If T0.13 runs first and
  renames `app/styles/*`, doing the directory move afterwards touches the same files twice.
  Cheap either way, but do them adjacently.
- My cost model is a reading of the code, not a rehearsal. I did not do the move in a worktree
  and prove it — so "cheaper than claimed" is a better-informed estimate, still an estimate.

## Confidence

**High** on the two corrections (both are one-line facts about how `meal-server.py` roots
itself, checked directly). **High** that deferring is right given the launchd state.

**Weakest link:** "not worth doing" is the kind of conclusion that is comfortable to reach and
hard to falsify. The honest counter-argument is that structure debt compounds silently and
someone will pay it later, in an unrelated task, without attributing it here. I think the
launchd precondition settles it regardless — but if the user's priority is a tidy tree rather
than a working phone, that ordering is theirs to overrule.

## What a full pass needs

The user grants Full Disk Access; `deploy.sh` reports "via launchd"; then this task reopens with
the sequence above. Until then it stays filed, not done-and-dusted.

## Reusable artifact

**Check how a static server computes its web root before assuming a directory move changes
URLs.** `directory=SCRIPT_DIR` means the tree can be reorganised without any client-visible
path changing — which flips the risk assessment for a PWA, where a URL change means invalidating
service-worker registrations on devices you cannot reach.

## Portability annotation

- **Generic:** the server-root question above; "don't restructure while the supervisor is
  broken"; LaunchAgent plists as out-of-repo state no test covers.
- **This-app-specific:** the FDA precondition, the five path sites, the CONTRACT coupling.
- **Library-schema-specific:** nothing.
