# T0.12 — Self-host the heading font

**Status:** DONE · verdict **PASS**
**Scope covered:** `@font-face` self-hosting, precache, licence provenance, offline proof, and a
weight audit. **Not covered:** a real phone; iOS Safari's font handling is not identical.
**Comparators:** network log before/after · `document.fonts.check` with the server **stopped** ·
the 10-combination computed-style battery against a re-taken baseline · cache-contents listing.
**Denominator:** states 2 and 4b — working tree, and a service worker serving a genuinely
offline page.
**Prior findings read:** `findings/T0.8.md`, `knowledge/instruments.md`.

## Headline

The heading font is served from the repo and precached, so it survives offline — **proved with
the server killed**. Two files, not four: Schibsted Grotesk is a variable font, so `latin` and
`latin-ext` cover the whole 400–700 range in 67 KB.

**And a caveat that lands on T0.7 and T0.8, not on this task:** their computed-style baselines
were captured while the webfont was still loading. Their conclusions survive; their coverage was
narrower than stated. Details below.

## What changed

- `app/assets/fonts/schibsted-grotesk-latin.woff2` (46,864 B) and
  `…-latin-ext.woff2` (20,844 B), fetched from `fonts.gstatic.com` (v7) on 2026-08-04.
  Both verified as real WOFF2 by magic bytes (`wOF2`).
- `app/assets/fonts/LICENSE.md` — SIL OFL 1.1, the two source URLs, sizes, and how to re-fetch.
- Two `@font-face` rules at the top of `app/styles/01-tokens.css`, `font-display:swap`,
  `font-weight:400 700`, with Google's own `unicode-range` values preserved.
- The `<link>` to `fonts.googleapis.com` deleted from `index.html`.
- Both fonts added to `sw.js` `ASSETS`; `CACHE` v31 → v32.

## Evidence

**Comparator 1 — the network log.** Every request on a fresh load goes to `localhost:8766`.
**Zero** to `fonts.googleapis.com` or `fonts.gstatic.com`. Confirmed structurally too:
`[...document.querySelectorAll('link')]` filtered for either host → `0`.

**Comparator 2 — offline, for real.** I killed the server (`curl` → `000`, connection refused),
then reloaded. The app rendered from the service-worker cache, and:

```
OFFLINE_check600: true      OFFLINE_check700: true      fontsStatus: "loaded"
```

The cache listing confirms why: `mealplanner-v32` holds 31 entries including both `.woff2`
files. **Before this change `sw.js` contained zero font entries** and the font came from a
remote origin, so an offline phone had no copy to fall back to — the failure did not need
measuring, it followed from the absence.

**Comparator 3 — nothing else moved.** The full 10-combination battery (5 screens × 2 themes)
against a re-taken baseline: **0 mismatches**.

**The weight audit — two files instead of four.** The old `<link>` requested weights
400;500;600;700. Measuring what the app actually renders, across all 10 screen×theme
combinations:

| weight | elements using the head font |
|---|---|
| 600 | 342 |
| 700 | 10 |
| 400, 500 | **0** |

`document.fonts` agreed: only the 600 and 700 faces ever reached `loaded`. Then the CSS itself
settled the file count — Google returns **two** distinct URLs for all four weights, because the
family is variable. So four weights were always two files. I kept the full `400 700` range
rather than subsetting to 600–700: it is the same two files either way, and it means a future
style that reaches for 500 cannot silently fall back. Recorded in `LICENSE.md`.

## The caveat for T0.7 and T0.8

Applying this change made all 10 hashes differ. That looked like a regression and was not.
Stashing T0.12 and re-measuring *with fonts fully loaded* reproduced **exactly** the same
values I was getting with T0.12 applied — so the delta was the font-load state, not the change.

The baselines used by T0.7 and T0.8 (`39:5ae73295` and friends) were therefore taken while the
webfont was still loading, with fallback metrics in `height`. Those tasks compared
fallback-state to fallback-state consistently, so **their conclusions hold** — but they never
exercised the loaded-font state, which is what a user actually sees. This task's baseline
(`39:77b78797` and friends) is the loaded-font one and is the right one to carry forward.

Practical rule, now in `knowledge/instruments.md`: **check `document.fonts.status === 'loaded'`
before measuring anything that includes text metrics.** `font-display:swap` guarantees a window
where you will measure the wrong thing, and the zero-timer pattern makes it *more* likely to
land in that window because it does not wait.

## What could break this

- **iOS Safari is untested.** Everything here is Chromium in a desktop pane. Safari's WOFF2 and
  variable-font support is fine in principle; its service-worker eviction is the risk, and no
  phone has been touched.
- **`v7` is pinned by filename, not by contract.** These are Google's hashed asset URLs; if the
  family updates, ours does not — which is the point of self-hosting, but it means a future
  glyph fix will not arrive on its own. `LICENSE.md` records how to re-fetch.
- **Only two subsets.** `latin` + `latin-ext` is what the old `<link>` served for this UA, so
  this is not a regression, but a recipe title in, say, Greek or Cyrillic now falls back to
  `system-ui` with no network path to a fix.
- `01-tokens.css` now opens with 20 lines of `@font-face` before the tokens it is named for. If
  T0.13's rename happens, fonts arguably deserve their own file.

## Confidence

**High.** The offline check is the deliverable and it was run with the server dead, not
simulated. The no-external-request claim is confirmed two independent ways. The style battery is
unchanged against a same-state baseline.

**Weakest link:** the "before" half of the offline claim is an argument, not a measurement — I
never observed the old build failing offline, because this machine has internet and only the
local server was stopped, so `fonts.gstatic.com` would still have resolved. What is measured is
that the font was in no cache and came from a remote origin; the offline failure follows from
that necessarily, but I did not watch it happen.

## What a full pass needs

1. Open the installed PWA on the phone, in aeroplane mode, and look at a heading.
2. Decide whether `@font-face` belongs in `01-tokens.css` or its own file (T0.13).
3. A follow-up could drop `latin-ext` (21 KB) if the library is confirmed Latin-1 only —
   not worth a task on its own.

## Reusable artifact

**How to self-host a Google font correctly**, in four steps that each catch a real trap:

1. Fetch the CSS **with a modern browser User-Agent** — the endpoint serves `woff2` only to UAs
   it believes support it, and `ttf` otherwise.
2. Count *distinct* `src: url(...)` values, not `@font-face` blocks. A variable family returns
   the same file for every weight; eight blocks were two files here.
3. Copy Google's `unicode-range` values verbatim, or the browser downloads both subsets for
   every page instead of only what the text needs.
4. Precache the files **and** bump `CACHE` — a self-hosted font that is not precached has simply
   moved the offline failure, not fixed it.

## Portability annotation

- **Generic web:** all four steps above; `document.fonts.status` gating before measuring text
  metrics; killing the origin server as a real offline test for a precached PWA.
- **This-app-specific:** the file paths, `ASSETS`/`CACHE` coupling, the 600/700 weight finding.
- **Library-schema-specific:** nothing.

A **fresh clone** now carries its own fonts — one fewer external dependency, and the app renders
correctly with no network at all.
