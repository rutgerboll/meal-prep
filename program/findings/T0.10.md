## Headline

`git status --porcelain` is now empty on a live checkout with the server rewriting the seed
underneath it, and **`deploy.sh` completed for the first time** — but it completed by falling
back to a manual process, because the launchd job's own stderr says
`Operation not permitted`. **Full Disk Access is missing after all, and my v1.1 "correction"
retracting that diagnosis was wrong.**

## What changed

- `.claude/launch.json` ignored. It is machine-specific browser-pane config and it was

## The decision, and why I did not do what the proposal said

The brief offered (a) untrack and ignore, or (b) exempt the path from the guard, and
`knowledge/structure-proposal.md` leaned (a) *with* a move to `dist/`. I did (a) **without**
the move.

**Untracking is what fixes deploy; the move is cosmetic.** They are separable — the brief says
so — and the move costs edits to four path sites (`build_seed.py`'s output path and
`THUMB_CACHE_PATH`, `embed_seed.py`'s `SEED_PATH`, `meal-server.py`'s read) that T0.11 would
redo. Doing it now buys clarity and spends risk on a live server. I folded the move into
T0.11's decision. If T0.11 concludes "not worth doing", `app/seed.json` stays where it is,
ignored — which is a perfectly good end state, because the `.gitignore` entry now says plainly
what the directory layout would only have implied.

Rejected (b) outright: it leaves a tracked file that mutates under you, so every `git add -A`
stays dangerous (`knowledge/prioritization.md` G5).

**Nothing besides the pipeline reads `seed.json`** — verified by grep across `app/js/*.js`,
`index.html`, `sw.js` and `scripts/`. The app boots from the inline `SEED` and syncs from
`/sync.json`. So untracking cannot break a client.

## The incidental finding, which matters more than the task

`deploy.sh` printed `launchd didn't bring a healthy server up — starting one manually
instead`. So the new health check rejected the launchd server. Its stderr explains why:

```
/Library/Developer/CommandLineTools/usr/bin/python3: can't open file
'…/app-build/app/meal-server.py': [Errno 1] Operation not permitted
```

Nine occurrences, `last exit code = 2`, job in `spawn scheduled` respawn-throttle.

**Errno 1 is EPERM, not ENOENT (2).** The path is right and the file is present — I read it
from this shell in the same breath. A permission denial on a path under `~/Documents`, for a
binary invoked by a LaunchAgent, is precisely the Full Disk Access failure `SYNC-SETUP.md`
documents.

**So CONTRACT v1.1 was wrong and v1.0 was right.** In T0.1 I diagnosed FDA from a matching
documented failure mode; then an accidental `pkill` produced a healthy process at 14:08 and I
retracted the diagnosis as refuted. The retraction was the error. I never read
`/tmp/mealplanner-server.err` after the restart — I had checked it *before*, when it did not
exist, and never went back. The evidence was sitting in a file the whole time.

What is still unexplained: why the 14:08 process ran healthily at all. It carried launchd's
full-path argv, yet launchd cannot exec that path now. I am not going to guess a third time.
It does not change the remedy.

**Production is currently served by `deploy.sh`'s manual fallback** (pid 63918, `PPID 1`,
started 15:33). It is healthy and survives this session, but it will not survive a reboot or
logout. That fallback existing is why the phone works right now.

## What could break this

- **A reboot takes the app down** until someone re-runs `deploy.sh`, because launchd still
  cannot start it. This is now the top operational risk on the board.
- A fresh clone has no `seed.json` until `build_seed.py` runs, which needs `MP_BASE_DIR` and
  the parent library. The app still boots offline from the inline `SEED`; only sync is dead.
  Nothing in the repo tells a new clone this — `CLAUDE.md` should, and does not yet.
- `.gitignore`ing `app/seed.json` means a genuinely *wanted* seed commit (T0.3's job) now needs
  `git add -f`. That is the correct trade but it is a sharp edge; T0.3's brief should say so.

## Reusable artifact

The park-merge-restore sequence, for untracking a file a live daemon owns:

```
cp app/seed.json /tmp/seed.live.json && mv app/seed.json /tmp/seed.parked.json
git merge --no-ff <branch>
[ -f app/seed.json ] || mv /tmp/seed.parked.json app/seed.json
```

The merge refuses otherwise, and forcing it would delete a file the running server is serving
from. Checking `[ -f ]` before restoring matters: the server may have regenerated it in the
gap, and its copy is the fresher one.
