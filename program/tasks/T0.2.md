## Why this task exists

T0.1 measured two guards that report success while the thing they guard is broken. Neither is
a hypothesis; both were reproduced.

1. **`scripts/pre-commit` does not cover `app/js/*.js`.** `app/sw.js` precaches every file in
   `app/js/`, and the service worker is cache-first with no revalidation — so a JS-only commit
   is **permanently** invisible to an installed phone. T0.1's probe A staged `app/js/pwa.js`
   alone and it committed clean; probes B/C/D confirm the hook works correctly for
   `index.html`. The fix is one more path in the hook's `grep`.
2. **`app/deploy.sh` declares the server healthy on `lsof -i :8765 -sTCP:LISTEN`.** This is not
   hypothetical: the launchd server spent 2026-08-01 → 08-04 holding that port while returning
   404 to every request, and nothing surfaced it. `deploy.sh` would have printed ✓ over it. It
   should `curl` a real path (`/index.html` and `/sync.json`) and check the status code.
   Consider whether the same check belongs somewhere that runs without a deploy, since the
   outage's whole character was that nobody was looking.

While you are in `deploy.sh`: its `git status --porcelain` guard refuses **permanently**,
because `meal-server.py` rewrites the tracked `app/seed.json` on every `/sync.json` request
(GOTCHAS 2026-08-04). As written, the documented deploy path cannot run. Decide and implement
one of: ignore `app/seed.json` in the guard, or stop tracking it. Say which and why —
`knowledge/prioritization.md` G5 is the constraint that the user's food data must not ride
along in unrelated commits, and either option must still honour it.

## Known traps

- **Test the hook, don't read it.** T0.1's method: throwaway commits on a task branch, then
  `git reset --hard <base>`. A hook that "looks right" is one comparator (CONTRACT §4).
- Cover the negative case too — a `sw.js`-only change, and a JS change *with* a bump, must
  still commit.
- Do not test `deploy.sh` by running it. It pulls. Exercise its checks in isolation.
