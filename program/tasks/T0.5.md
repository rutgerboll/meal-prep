## Why this task exists

The user has a vague sense the UI is behind. T0.1 found a concrete reason that feeling would
be hard to shake: **the app ships two conflicting design-token sets and two design-system
documents**, so "what is this app's current UI?" has no single answer to check against. Settle
what the app actually does before judging whether it is current.

## The stack, stated plainly, because it constrains the answer

No framework, no build step, no npm. Plain HTML + inline CSS + 16 `<script src>` files of
vanilla JS, IndexedDB for storage, a service worker for offline. This is **deliberate** —
keyless, offline-first, served from a Mac mini (`CLAUDE.md`, `program/README.md`
§Anti-patterns). "Latest conventions" therefore means *modern CSS and modern web platform
features*, **not** "should this be React". A recommendation to adopt a framework is
out of scope and contradicts a settled decision; say so if you are tempted.

## Start from what is already measured

Read `knowledge/structure-proposal.md` §1 first. It establishes with counts: 23,531 bytes of
CSS in three inline `<style>` blocks; 29 of block 1's 31 `:root` tokens dead; 20 `!important`
declarations; block 1's 125 base selectors still live; `DESIGN-SYSTEM.md` (Sage, current)
versus `design/design-system.md` (383 lines, June, self-declared "source of truth"). Do not
re-derive those numbers.

## In scope

- Inventory the real component vocabulary from the CSS and the `screen-*.js` renderers — rows,
  chips, cards, nav, modal, toast, the Cook screen's typographic style.
- For each, the requested table: **component → what it does now → current practice → migration
  cost**. Anchor "current practice" in something checkable: CSS nesting, `:has()`,
  `color-mix()`, container queries, `light-dark()`, cascade layers, `dialog`, `popover`,
  view transitions, logical properties, `prefers-reduced-motion`, focus-visible.
- Judge against `DESIGN-SYSTEM.md` (Sage) — CONTRACT §9 makes it the benchmark for anything
  visual — and note where the code contradicts it.
- Accessibility is fair game and usually where a hand-rolled UI is genuinely behind: focus
  states, contrast against the Sage tokens, hit targets, semantics of tappable `div`s.

## Out of scope

- **Any change to `app/`.** Audit only. File follow-ups instead.
- Framework or tooling adoption (see above).
- The layout/refactor question — that is T0.6, running alongside. **Coordinate:** you will both
  meet the duplicate-token finding. Agree who writes it up; duplicating it wastes the user's
  money and produces two subtly different accounts of one fact.

## Known traps

- **Verify in the browser, not in the file.** With three cascading blocks and 20 `!important`s,
  what a selector *says* and what a screen *renders* are different questions. CONTRACT §3:
  reading source is a hypothesis. Use computed styles.
- Certify the server before measuring on it (CONTRACT §3) — a listening port is not a working
  one, and this project has already been burned by that.
- Test both themes. The app defaults to `data-theme="dark"`; the light path is easy to break
  and easy to forget to look at.
- "Not the latest" is not the same as "wrong". A pattern that works, is small, and has no
  accessibility defect is not debt because a newer syntax exists. Cost the migration honestly
  and let some rows say "leave it".

## Done when

`findings/T0.5.md` per CONTRACT §6 carries the component table, names which gaps are real, and
files a follow-up task per real gap — or states plainly that the UI is current enough and the
user's hunch was the token duplication all along.
