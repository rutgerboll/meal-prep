# T1.2 — Teach `meal-planner` to nudge an un-captured cookbook-backlog photo

**Wave:** 1 — close the schema loop (skill side) · **Effort:** medium · **Model:** Opus 5
**Depends on:** T0.1, T1.1 · **Reads:** findings/T0.1.md, findings/T1.1.md

> Read README.md and CONTRACT.md first. §2 excludes the Claude-side skills by default; this
> brief scopes in `meal-planner` and nothing else. §5 matters here: do not generalize from
> one generated plan — plans vary in length and meal slots, so say which shapes you tried.

## Why this task exists

The cookbook backlog is photos of recipes the user meant to cook and hasn't. The app now
*displays* it well (3-up thumbnail grid, "＋ Capture" overlay, thumbnails on captured rows,
done 2026-06-25), but display was never the bottleneck — nothing ever *suggests* one, so
the backlog only shrinks when the user remembers it exists. ROADMAP #5 flags the remaining
piece as inherently Claude-side: the app is keyless and offline, so the nudge has to come
from the planner. T1.1 makes captured recipes carry an `image`; this closes the loop by
sending the user back to the pile.

## Objective

Make `meal-planner` periodically surface an un-captured backlog photo as a candidate when
building a plan — often enough that the backlog actually drains, rarely enough that it
doesn't crowd out the library or fight the planner's existing balancing (cuisine spread,
liked recipes, base/finish structure).

## In scope

- The `meal-planner` skill definition only.
- Deciding and **writing down** the nudge policy: how often, at what point in planning, and
  what makes a backlog photo a good candidate right now.
- The hand-off: a nudged photo that the user accepts must route through `recipe-capture`
  (T1.1) before it can land on a plan — a plan may not reference a recipe that isn't in the
  library, or the grocery sum breaks.
- Not nagging: a declined suggestion shouldn't come back next week unchanged.

## Out of scope

- **`recipe-capture` — that was T1.1.**
- Changing the app's backlog screen. It already does its job.
- Auto-capturing a photo without the user choosing it. Capture is a judgment call on an
  image; silently inventing a recipe from a photo is worse than not suggesting one.

## Starting points

- `ROADMAP.md` Part 2 #5 ("the planner periodically suggesting a backlog recipe belongs in
  the `meal-planner` skill")
- findings/T1.1.md — the capture path this depends on, and whether skills are editable here
- `app/build_seed.py` + `app/js/cookbook-backlog.js` — how backlog entries and their
  captured/un-captured state are actually represented
- `preferences.md` in the parent library — the planner's existing constraints

## Known traps for THIS task

- **Skill reachability** — same trap as T1.1. If T1.1 concluded the skills can't be edited
  from a session, this task's deliverable is a patch spec too. Don't rediscover that.
- The planner already balances several things at once (cuisine adjacency, liked recipes,
  base capacity, week-2-from-freezer mirroring). A nudge that ignores those produces a plan
  the user rejects wholesale, which is worse than no nudge.
- "Un-captured" is state that lives in the library, not the app. Verify how it's determined
  before keying the policy off it.
- Batch-prep reality: fresh components are assembled day-of and never portioned ahead — a
  backlog suggestion that assumes make-ahead portioning will read as wrong.

## Deliverable

`findings/T1.2.md` per CONTRACT §6, plus the edited skill (or patch spec), plus the nudge
policy written down somewhere durable — `knowledge/` if it's a fact about the system, the
skill itself if it's behavior.

## Done when

Generating a plan surfaces a backlog candidate at the intended rate across at least two
differently-shaped plan requests (§5), an accepted candidate reaches the library through
`recipe-capture` and then a plan, and a declined one doesn't immediately reappear.
