# T1.1 — Teach `recipe-capture` the schemaVersion-2 keys

**Wave:** 1 — close the schema loop (skill side) · **Effort:** medium · **Model:** Opus 5
**Depends on:** T0.1 · **Reads:** findings/T0.1.md

> Read README.md and CONTRACT.md first. Most likely to be broken here: CONTRACT §2 puts the
> Claude-side skills **outside** default scope — this brief is the explicit exception that
> puts `recipe-capture` in scope, and nothing else. And §4: a skill that "looks right" is
> one comparator; you need a captured recipe that survives `build_seed.py` **and** shows up
> in the app.

## Why this task exists

ROADMAP #5 and the Phase-2 schema note both end on the same unfinished sentence. The app
side of schemaVersion 2 shipped on 2026-06-25: `build_seed.py` parses `thaw_hours_ahead`,
`prep_ahead`, and `image`; the app surfaces thaw reminders, the 🌙 Prep ahead card, and
thumbnails; sync flows them through. But the **capture** side never learned the keys, so
nothing new writes them. The pipeline is live and dark — 52 `IMG_*.jpeg` files sit in
`recipe pics/` with no recipe pointing at them, and every recipe captured since the
migration is a schemaVersion-1 recipe in a schemaVersion-2 world.

## Objective

Make the `recipe-capture` skill emit `image`, `thaw_hours_ahead`, and `prep_ahead` in
recipe frontmatter whenever the source supports them, such that a recipe captured through
the skill lights up thaw reminders, the prep-ahead card, and a thumbnail in the app with no
manual editing of the markdown.

## In scope

- The `recipe-capture` skill definition only.
- The three keys, their formats per ROADMAP's Phase-2 schema block (`thaw_hours_ahead:` int
  or null; `prep_ahead:` a list; `image:` a filename in `recipe pics/`).
- When to populate each: freezer-bound proteins get a lead time, night-before steps get
  lifted out of the method into `prep_ahead`, a photo-sourced capture records its own filename.
- Backward compatibility: a schemaVersion-1 recipe missing all three must keep parsing.

## Out of scope

- **`meal-planner` — that is T1.2.** Don't do both in one session.
- Retro-fitting the existing recipe library. Assigning images to the 52 backlog photos is
  the user's curation call, not a code change; if this task makes it cheap, say so in the
  findings and stop.
- Anything under `app/`. If the parser turns out to be wrong, `tm log READ-FIRST` and raise
  it — don't fix it here.

## Starting points

- `ROADMAP.md` → Part 2 #3, #5 and Phase-2 "schema (schemaVersion 2)" block — the
  authoritative key list
- `app/build_seed.py` — the certified reader (CONTRACT §3); its parsing *is* the spec

- The parent library's existing recipes as format examples

## Known traps for THIS task

- **The skills may not live on this filesystem.** Onboarding could not find them under
  `~/.claude/plugins` or anywhere obvious; they are surfaced to sessions as
  `meal-planning:recipe-capture` without a discoverable path. Resolve this **first** — if
  they can only be edited through the desktop app, the deliverable is a precise patch spec
  for the user, not an edit, and the brief's "Done when" changes accordingly. Say which.
- `build_seed.py` needs `MP_BASE_DIR` from a worktree (GOTCHAS).
- Writing a test recipe into the real library pollutes shared state the user cooks from.
  Use an obviously-named throwaway and remove it, or work in a copy.
- The `image:` value is a filename relative to `recipe pics/`, not a path. Thumbnails are
  cached by `(path, mtime)` — a renamed file re-generates.

## Deliverable

`findings/T1.1.md` per CONTRACT §6, plus either the edited skill or a copy-pasteable patch
spec, plus one worked example: a recipe captured through the new path, shown parsing and
rendering.

## Done when

A recipe captured via the skill produces all three keys where applicable, `build_seed.py`
picks them up, and the app shows the thaw reminder / prep-ahead card / thumbnail — verified
in the running app, not inferred from `seed.json`.
