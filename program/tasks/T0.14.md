## Why this task exists

**The phone is served directly from the working tree we develop in.** Raised by the user on
2026-08-04 ("I want to make sure we are not developing in the same spot as we are deploying"),
and confirmed by measurement rather than by reading:

- The launchd job runs `…/app-build/app/meal-server.py`; the running process's `cwd` is
  `…/app-build/app`; `git rev-parse --show-toplevel` is `…/app-build`. Same directory.
- `meal-server.py` serves `directory=SCRIPT_DIR`, so the web root **is** the dev checkout.
- Demonstrated: appending a comment to `app/index.html` — uncommitted — and `curl`ing the
  production URL returned it **immediately**. No commit, no review, no deploy step.

Consequences, all live today:

1. **A merge to `main` is a deploy.** Wave 0d shipped to the phone the moment each task merged.
   That worked out, but nothing made it a decision.
2. **Ordinary git operations move production.** `git checkout`, `stash`, `rebase` all rewrite the
   served tree. T0.10's park-merge-restore dance briefly removed `app/seed.json` from under a
   live server; that was reasoned about, but it should not have needed reasoning about.
3. **`deploy.sh` is decorative.** Its `git pull --ff-only origin main` runs *in the checkout the
   code already lives in* — verified a no-op (`0 behind, 0 ahead`). It restarts the server and
   health-checks it, which is real; it does not deploy anything.
4. Program artifacts **must** be edited in the main checkout (README's write rules), so "never
   touch `app/` in main" is a discipline no mechanism enforces.

Worktrees have been mitigating this — wave 0d did every code edit in
`.claude/worktrees/wave-0d` — but that is convention, and it ends at the merge.

## Objective

A deploy target that is a **different directory from the one we edit**, with an explicit
promotion step, and `deploy.sh` doing something real.

## The shape that fits this system

A **sibling git worktree on a `release` branch** — not a second clone:

```
Meal planning/
  app-build/     ← dev. main. worktrees under .claude/worktrees/. Never served.
  app-deploy/    ← git worktree of the same repo, pinned to `release`. Served. Never edited.
  recipes/ meal-plans/ …   ← the library, shared by both
```

Two properties worth knowing before you design something else:

- **The library path resolves for free.** `build_seed.py` and `meal-server.py` derive their base
  as `SCRIPT_DIR/../..`. From `app-deploy/app` that is `Meal planning/` — the same directory it
  resolves to from `app-build/app`. Verified. **No `MP_BASE_DIR` needed in the plist.**
- **A worktree shares `.git`**, so this costs ~300 KB of working files, not a second clone, and
  the `pre-commit` hook (in `.git/hooks`) applies to both.

Deploy then becomes: fast-forward `release` to `main` in `app-deploy`, restart, health-check.
That is a promotion, and it is revertible by moving `release` back.

**Consider whether `release` should lag `main` deliberately** (promote when you choose) or track
it (promote on every push). Recommend one, in the finding.

## Gate: verify the current service and plan a supervised switch

Repointing the LaunchAgent at `app-deploy/app/meal-server.py` means editing
`~/Library/LaunchAgents/com.mealplanner.server.plist` and switching a live
service. On 2026-09-23 the current launchd job was running and both
`/index.html` and `/sync.json` returned 200. The August Full Disk Access gate
is no longer a verified blocker. Before implementation, inspect the current
plist, process, worktrees, and rollback path, then perform the switch with
service health checks. T0.11's directory move remains deferred; do not assume
it is part of this task.

## Known traps

- **The deploy worktree starts with a cold `.thumb-cache.json`**, so its first `/sync.json` runs
  `build_seed.py` cold — 7.4 s on a good day and minutes under load (T0.2 measured a 45 s ceiling
  producing a false negative). Warm it before health-checking, or the first deploy looks broken.
- **`tailscale serve` points at port 8765**, not a path — it needs no change. Confirm rather than
  assume.
- **Do not `git worktree add` inside `app-build/`.** A sibling of `app-build` keeps the `../..`
  library resolution correct; nesting it does not.
- The `release` branch must never be checked out in `app-build` — git refuses a branch checked
  out in two worktrees, which is a helpful guard rather than an obstacle.
- Program artifacts stay in `app-build`; update their path references if needed.
